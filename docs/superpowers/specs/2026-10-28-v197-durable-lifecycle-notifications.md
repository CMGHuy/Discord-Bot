## Goal

Make admin close/cancel notifications reach Discord despite transient failures or process restarts. A lifecycle event must remain pending until Discord acknowledges its message. The operator can identify repeated deliveries. This recovers actionable information already generated by the bot; it changes no entry, exit, sizing, expiry or trading gate.

## Evidence and boundaries

The evidence document records source-level delivery loss, not a production incident or measured trading-performance lift. `swingbot/admin/api_v1/trade_commands.py` queues `kind=plan_transition` with uppercase plan statuses. `swingbot/commands/scanning/loops.py:_post_manual_close_queue` sends those rows to `swingbot/core/scanning/lifecycle_embeds.py:notify_closed_trades`, which skips them. `swingbot/core/db/repositories/notify_queue.py:drain` deletes before sending; swallowed exceptions permit a false posted log.

Scope covers existing manual-close queue producers, plan close/cancel notifications, and their consumer. Scheduled signal issuance and unrelated notification families are separate delivery paths and are not silently folded into this change. Implementation begins after v194 merges, or explicitly rebases onto its merged result. Recheck producers and tests then.

## Decisions

Partner decision, 2026-10-28: retry until delivered; possible duplicates must be identifiable. Delivery is at least once, not exactly once. A send acknowledged by Discord but followed by a database/process failure may be retried. No paid provider or external queue.

## Event contract

Keep the existing Postgres notification queue as the single durable source. Persist a stable event ID, explicit event kind, target channel, creation time, immutable rendering payload, attempt count, next attempt time, lease owner/expiry, last error and delivered message ID/time. Promote only fields required for due-event selection, lease ownership and indexing; follow schema-evolution.md and justify promotions. Existing payload fields remain in doc where possible.

Kinds are `trade_closed` and `plan_transition`. The latter supports CLOSED and CANCELLED with separate human-readable titles. An event snapshot contains ticker, direction, plan/trade IDs, prior/new status, reason and transition time; closure events also preserve the recorded fill and result fields needed by their renderer. Renderers consume the recorded snapshot, never a later version of the trade. A cancellation must never be presented as a filled or closed position.

Use an event ID derived from a durable transition identity, not merely plan ID/status: two distinct transitions must not collide. Persist the same ID on retries. Display it in the Discord footer. Do not rewrite alert numbers or recalculate fills during delivery.

## Atomic recording and migration

Record the transition and its delivery event in the same database transaction. For a close involving both trade and plan updates, all state writes and event insertion share that transaction. Extend repository transaction interfaces narrowly if required. On failure, roll back the transaction and return an explicit failed admin action; never report success without a queued event. Preserve issuance StoreWriteHalt behavior elsewhere.

An Alembic revision upgrades existing queued rows. Legacy trade snapshots become trade_closed; explicit plan_transition rows retain their kind and recorded status. Assign stable IDs once in the migration. Incomplete legacy plan snapshots are retained as visibly blocked delivery records rather than invented fills. No read-time shape upcasting. Do not delete pending events on upgrade or downgrade. Migration/downgrade tests must preserve payloads and pending work; halt bot consumers during the migration so an older DELETE-based consumer cannot drain new work. Execution/deployment authorization remains separate from these documents.

## Delivery state machine

A short Postgres transaction atomically claims due events using row locking and a lease. Release the transaction before network I/O. Use a 120-second lease and a bounded 30-second send operation; reclaim an expired lease after a crash. Claim each event immediately before its send (never pre-lease a batch waiting on sequential I/O). Process at most 20 events per monitor tick; isolate each event so one bad destination does not block another. Verify owner/token on success and failure updates so an expired worker cannot overwrite a newer claimant.

On a successful send, persist Discord message ID and delivery time before removing the event from pending work. Retain delivered records for seven days, then prune only acknowledged rows. A failed acknowledgement leaves the event eligible for retry. Never delete before acknowledgement.

For retryable failures, retain the event and schedule delays of 5, 15, 60, 300, then 900 seconds (900-second cap indefinitely); honor Discord retry_after when longer. Record attempts and a sanitized last error. Missing destination, permission denial, malformed payload or unavailable channel remain durable and visibly blocked; retry at the capped interval so repaired configuration resumes without data surgery. Resolve destination at enqueue time; configuration changes require an explicit audited retarget of undelivered events, never implicit rerouting.

Log attempted, acknowledged, retried and blocked counts separately. A returned coroutine is not proof of delivery. On every blocked state transition, emit an ERROR with event ID, kind, queue age and sanitized cause. Expose queue pending count, oldest pending age and blocked count in the existing operational health API, preserving unavailable as unknown. Give the operator a visible admin warning when blocked > 0 or oldest pending age > 15 minutes. Include mobile/tablet/desktop rendering and accessible explanatory text. Do not expose tokens or raw credentials.

## Failure and rollback

Database outage before transaction commit leaves no successful action. Outage after Discord acceptance may create an identifiable duplicate after recovery. Process death before send is recovered by lease expiry. Repeated channel failures retain backlog and surface the warning. No guarantee exists while Discord or Postgres remains unavailable; no retry limit silently discards work.

Rollback requires stopping the new consumer before application/schema rollback. Preserve the queue and take a database backup; never deploy the old drain consumer against new pending events without an explicit compatibility conversion and inspection. Prefer rolling application code forward to repair delivery. Follow DB_RESTORE.md for any point-in-time restore, which is separately authorized.

## Success

- Close and cancel each render the correct event once on an error-free path.
- Failure on channel resolution/send leaves pending work with a later due time.
- Restart after claim, concurrent consumers, expired leases, stale acknowledgements, and database failure after send all preserve delivery intent.
- A timeout/acknowledgement ambiguity repeats the same visible event ID.
- Migration preserves legacy queue rows; downgrade preserves undelivered snapshots.
- Admin action rollback, backlog health and correct delivery counts have regression coverage.
- New tests join one existing suite or register a new directory in tests/suites.toml; complexity stays below 15.
- Run replicate-prod-db into shared swing-db before database tests, then narrow tests per task. Run full backend and frontend suites once in the final plan task, plus the three-width layout audit. No tests or production operations are run merely to author this spec.

## Parallelisation

Sequential: transaction/event contract and migration precede renderers and the lease consumer; the health projection and UI consume the final queue contract. Regression integration and final verification follow all changes. Execute one agent at a time unless the partner explicitly authorizes parallel work.

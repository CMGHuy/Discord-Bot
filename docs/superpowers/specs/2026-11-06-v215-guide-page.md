# v215 — Guide: a living guidebook page under Insights

**Version:** ui 1.40.0 · bot 2.17.0
**Bump:** ui minor (a new Insights section every user sees), bot patch (new read-only admin API endpoints; nothing in Discord changes)
**Edge:** none (integrity)
**Screen:** exempt (integrity)
**Panel:** technical-analyst, risk-manager, financial-advisor

## Why

On 2026-11-06 the partner asked for a page under Insights that explains the bot
the way a guidebook would: how levels are found, how trades are built,
filtered, sized and closed, and how the algorithm works. It must stay current
whenever the bot changes.

The explanation that exists today is not fit for that. `docs/strategy/`,
`docs/strategy-types/` and `docs/features/` hold about 2,800 lines, written for
developers and partly stale ("code is authoritative where these tables lag",
`docs/strategy/strategy.md`). Nothing in the admin site explains an alert, a
badge, the 2% cap, or why a quiet day happened. Someone who trades from the
alerts has to read code or ask.

The guide serves three readers at once (partner, 2026-11-06): newcomers from
Discord, traders who act on the alerts, and developers. It therefore has three
layers on every chapter, described below.

### Three layers per chapter

1. **In plain words**: a short callout at the top of the chapter for the
   newcomer. No formulas.
2. **Main text**: trader level, with the real formulas and the live numbers.
3. **Under the hood**: collapsible boxes naming the module, config key and exact
   algorithm, for developers. Collapsed by default.

### Page behaviour

- **Table of contents**: sticky left rail on desktop, a drawer on tablet, a
  chapter picker on mobile (`ui-design.md` three-device rule; 44px touch targets).
- **Search**: client-side over chapter titles, headings and text, with an empty
  state ("No section matches …").
- **Deep links**: every heading has a stable anchor;
  `/insights/guide/<slug>#<anchor>` opens the chapter scrolled to it.
- **Freshness stamp**: each chapter shows "Reviewed for bot vX.Y.Z" from its
  front matter.
- **Contextual help**: a small `?` link (`GuideLinkComponent`) next to the alert
  fields shown in the admin site, the Risk page metrics and the Analytics
  metrics. It jumps to the matching guide anchor.

## Design

### Content: Markdown chapters in the repo

`docs/guide/NN-<slug>.md`, one file per chapter, each with front matter:

```yaml
---
title: Sizing and risk
slug: sizing-risk
order: 8
reviewed_for: 2.17.0
sources:
  - swingbot/core/planning/...        # paths the chapter describes
  - swingbot/config.py:MAX_RISK_PCT   # path:symbol pairs
---
```

Layer conventions in plain Markdown:

- `> **In plain words** ...` as the first block.
- `<details><summary>Under the hood</summary> ... </details>` for developer boxes.
- `{{name}}` placeholders for live values (next section).

The pipeline diagram is a checked-in SVG that uses the app's theme tokens, so
it reads in light and dark.

Chapters are **written from the code and checked against it**, not copied from
`docs/strategy/*`. Where those docs hold the deep version, the chapter links to
them. The existing developer docs are not rewritten by this spec.

### Live values: a whitelisted resolver

`swingbot/admin/guide/` holds:

- `chapters.py`: loads `docs/guide/*.md`, parses front matter, orders by `order`,
  extracts headings (for TOC and search) and builds anchors.
- `placeholders.py`: a **fixed table** `name → function` returning Markdown.
  Examples: `config.MAX_RISK_PCT`, `horizons.table` (from
  `strategy_types.HORIZONS`), `strategies.cards` (registry plus badge tiers),
  `gates.list`, `version.bot`. No expressions and no generic config access:
  only listed names exist, so a secret can never be rendered. The exact
  placeholder list is settled in the plan from the code brief.
- An unknown placeholder raises at load time. The freshness test catches it in
  CI; at runtime the API returns 500 with the placeholder name logged, never
  the raw `{{…}}` text.

### API

Both routes need login, like every `/api/v1` route.

- `GET /api/v1/guide` → `{chapters: [{slug, title, order, reviewed_for, headings: [{level, text, anchor}]}]}`.
- `GET /api/v1/guide/<slug>` → `{slug, title, reviewed_for, markdown}` with
  placeholders resolved. An unknown slug returns 404.

Chapters are read from disk and cached per process. They change only with a
deploy, so no invalidation is needed beyond a restart.

### Frontend

- New `frontend/src/app/workspaces/guide/` (routes, page, spec), lazy-loaded at
  `insights/guide` and `insights/guide/:slug`, behind `authGuard`. It is added to
  the Insights sections in `shell/nav` and to `app.routes` (with the existing
  route spec tables updated).
- Markdown is rendered client-side with `marked` (the one new dependency, exact
  pinned version) and bound through Angular's sanitiser. The sanitiser keeps
  `details`/`summary`; the plan verifies this with a spec.
- The search index is built once from the chapter index plus the text of loaded
  chapters. Chapters load lazily; the index endpoint carries the headings, so
  heading search works before any chapter is opened.
- `GuideLinkComponent` (`ui/`): input `target: '<slug>#<anchor>'`, renders a `?`
  icon with an accessible label and a 44px hit area that does not grow its row
  (the lesson of commit 2a11a416).

### Freshness gate: how the guide stays current

Three layers, all part of this spec's deliverable:

1. **Content test** (pytest, a suite named in `tests/suites.toml`):
   - Every placeholder in every chapter resolves.
   - Every `sources:` path exists, and every `path:symbol` symbol is still
     defined there.
   - Every registered strategy and every horizon key appears in the guide
     (through `strategies.cards`/`horizons.table` or by name), so adding or
     removing one without touching the guide fails CI.
   - `reviewed_for` parses as a version no newer than `VERSION.json`'s bot line.
2. **Anchor test** (frontend spec): every `GuideLinkComponent` target used in
   the app names an existing chapter slug and heading anchor. The anchor list
   comes from a generated JSON fixture the backend test also checks, so the two
   cannot drift apart.
3. **Process rule**: `/close-out` Step 5b gains a guide check. A plan whose diff
   touches any path listed in some chapter's `sources:` updates that chapter's
   text where behaviour changed and bumps its `reviewed_for`, or records
   "guide: no reader-visible change" in the close-out commit. A helper script
   (`scripts/dev/guide_sources.py <base>..<head>`) prints which chapters a diff
   touches. The rule lands as one line in `CLAUDE.md`, the detail in
   `document-lifecycle.md` § Implemented plans keep the skills aligned, and
   their Codex mirrors (`AGENTS.md`, `sync_codex.py`) in the same commit.

## Delivery: one spec, three plans

| Plan | Contents |
|---|---|
| **A — Foundation** | Backend loader, resolver, API; frontend page (TOC, search, deep links, three widths); nav and routes; content test, anchor fixture, `guide_sources.py`, `/close-out` rule and mirrors. Chapters 1 (`what-it-is`), 3 (`pipeline` with diagram) and 12 (`glossary`), so the page is useful on release |
| **B — Trading core** | Chapters 4–8 (`levels`, `strategies` with live cards, `gates`, `trade-plan`, `sizing-risk`), each written from the code with `sources:` filled in |
| **C — Using it** | Chapters 2, 9, 10, 11 and the `GuideLinkComponent` placements on existing pages |

B and C both depend on A (loader, resolver and test must exist). B and C are
independent of each other, except that C's `?` links into chapters 4–8 wait
for B; C places those links last.

## Testing

- **Backend**: loader (front matter, ordering, anchors, a malformed file),
  each placeholder, an unknown placeholder fails loudly, no name outside the
  whitelist, both routes (auth, 404, resolved output), the content test above.
- **Frontend**: page render, TOC on each breakpoint, search hit and empty state,
  deep-link scroll, `details` survives sanitising, `GuideLinkComponent` target
  and hit area, the anchor test.
- **Layout**: a Playwright check of `/insights/guide` at mobile, tablet and
  desktop widths, logged in with `.env`'s admin credentials (never printed).
- **Mirror**: `tests/hooks/test_codex_mirror.py` green after the `/close-out`
  and `CLAUDE.md` changes.

## Out of scope

- Rewriting `docs/strategy/*`, `docs/strategy-types/*` or `docs/features/*`.
- A Discord `!guide` command (could come later and point to the page).
- Editing guide text in the browser; the text is changed in the repo only.
- Translations.
- Any change to trading behaviour.

## Risks

- **Content drift inside prose**: the gate catches removed symbols, strategies
  and horizons, but not a sentence that is now wrong about a rule that still
  exists. The process rule plus `guide_sources.py` is the backstop. Live
  placeholders keep every number out of hand-written prose.
- **Advice framing**: chapter 1 and the footer state the guide is education
  about a paper-trading tool, never personal financial advice
  (financial-advisor seat).
- **Size**: twelve chapters of real content is the expensive part. That is why
  it is split across plans B and C, written chapter by chapter.

**Goal:** Make the live paper book profitable by (a) guaranteeing every winning trade banks **≥2.5%**, (b) cutting the two cohorts that produce ~100% of the losses, and (c) retraining the whole parameter surface on the **25 years of daily history already on disk** instead of the bull-heavy 2020–2023 window that produced the current settings. Training moves from `data/backtest_cache/` — which does not exist on the live server — onto a no-network bridge from the existing `market_data/daily/` corpus.

**Tech Stack:** Python 3.11, pandas/numpy, pytest, existing `scripts/` backtest + walk-forward harness. No new dependencies. No ML in the live path.

### Root cause is structural

`plan_engine.py:170-197` computes `TP1 = entry ± risk_distance × rr`, with `rr` from
`STRATEGY_RR_OVERRIDE` (`strategy_types.py:217-232`, all values 0.30–0.40) floored at
`RR_FLOOR = 0.30` (`plan_engine.py:31`). The stop is the *full* `risk_distance` (1R).
A win therefore banks ~0.35R while a loss costs ~1R **by construction**:

- median designed TP1 distance = **0.85%** (v2 confluence path: **0.77%**)
- median designed stop distance = **2.19%**
- median designed R:R = **0.35**

The median winning trade *cannot arithmetically* reach 2%. This was deliberate —
tight targets buying a high win rate (`strategy_types.py:210-216` targets 80%+ WR) —
and is recorded as a frozen constant in `docs/claude/backtest-methodology.md:15`.
Live, the win rate bought (55.6%) is far below the win rate required (63.2%).

Journal exit efficiency confirms the waste: median **0.24**. The median winner had
**0.92R** of favourable excursion available; we took **0.35R**.

## Risks carried into execution

1. **Survivorship bias worsens with the 1999 window.** The watchlist is *today's*
   megacap winners (NVDA's 1999 bar is $0.0376 split-adjusted). Training long-biased
   strategies on 25 years of survivors overstates bullish edge. `STRATEGY_GATES`
   (`strategy_types.py:246-263`) already forces Fibonacci and RSI bullish-only — that
   may itself be the artifact. V21 exists to expose this and must be willing to
   report that the long-side edge is not real.
2. **The permutation stop rule already fired once.** Gatekeeper G100 found `p ≥ 0.05`
   for *every* strategy. If V22 fires again, the correct outcome is to record "no
   demonstrable edge" and stop, not to keep tuning.
3. **MFE-based projections are optimistic by ~0.3R** (measured: the method projects
   +0.14R for tier C, which actually lost money live). Projections are directional
   only; V24 and V26–V29 settle the real effect.
4. **Volume collapse is now intended, not a risk — but it must not starve the proof.**
   Per the human-partner directive of 2026-07-31, fewer and better trades is the
   goal: tier-A/B-only cuts 475 → ~138 per 26 days and the reachability screen cuts
   further, which is *desirable*. The one hard constraint is statistical: proving
   WR > 90% needs **N ≥ 59** (V6 Step 5), and V36's forward gate needs ≥10 A+
   signals. If selectivity drives N below what the proof requires, the answer is a
   **longer window**, never a looser filter.

### Is 90% win rate reachable at 2.5% targets? The evidence says no — read before setting expectations.

The 90% target and the 2.5% floor pull in opposite directions, and the original
system already made this trade *the other way*: it bought a high win rate precisely
by making targets tiny (0.35R), which is exactly what produced the +1.44% average win
this plan exists to fix. Win rate at a given target is not a free parameter.

Measured from the live journal (267 usable MFE entries), win rate by cohort as the
target widens — the median stop is 2.19%, so **2.5% ≈ 1.14R**:

| cohort | n | @0.35R (today, ~0.85%) | @0.9R (~2.0%) | @1.25R (~2.7%) |
|---|---|---|---|---|
| tier A | 30 | **90%** | 70% | 53% |
| tier B | 82 | **95%** | 59% | 46% |
| tier C | 142 | 84% | 35% | 28% |

**Every cohort hits ~90% only at the tiny targets we are removing.** At 2.5% the best
cohort (tier A) sits near **65%**, and that estimate is *optimistic* — the same method
predicts +0.13R for tier C, which actually lost money live, so it runs ~0.3R hot.

This does not make the directive wrong; it makes it a **search target rather than a
promise**. The legitimate path to a high win rate at 2.5% is a far more selective
entry filter than "tier A" — the top decile of a retuned quality score, plus regime
alignment, plus gatekeeper A+ — accepting very low trade counts. V17 and V20 search
for exactly that frontier. What the plan must not do is claim 90% by shrinking the
target back down, which would rebuild the original problem.

**Expected honest outcome: a small, highly selective cohort somewhere in the 65–80%
band at ≥2.5% wins, with positive expectancy.** That is a far better book than
today's 55.6% at +1.44%/−2.47%. If the search does find a ≥90% cohort at N ≥ 59,
excellent — but the plan is not built on assuming it exists.
5. **Unfreezing rr invalidates the badge registry**, which the 80%-WR validation
   underpins. Badges are stale between V9 and V25.
6. **The validation budget is down to ONE shot and it is already loaded.**
   `2026-07-27-edge-final-shot.md:3-6` records that 2024-2025 was already spent once
   on the round-1 registry build, and that edge-engine **E92 is that window's "one
   deliberate reuse"** — pre-registered in commit `0c0dd9f` but **never fired** (the
   file has no `## Result` section; `git diff HEAD` on it is empty). **V24 and E92 are
   the same shot.** If both are ever executed the budget is double-spent and every
   downstream number is tainted. V24 explicitly supersedes and retires E92.
7. **No tier cut has demonstrated edge.** G100's permutation test found every one of
   11 strategies at `p >= 0.05` (0.346–1.0); `2026-07-gate-decision.md:182-190`
   records **"Config changes applied: none."** The A+/A/B ladder that V14 would
   enforce has never earned statistical support on TRAIN. The live book disagrees —
   tier B is +18.1% (n=107) and A is +4.7% (n=31) against C at −67.7% (n=181) — but
   that is 26 days of one regime. V14 proceeds on *live* evidence while recording
   that TRAIN says the ladder may be noise.
8. **Full-scale permutation is hardware-infeasible, not merely slow.** E90 measured
   `--n 200` at **300+ hours** of continuous compute on this machine, and E91's
   sensitivity table at ~13 hours with a tooling gap (`--full --portfolio` do not
   compose). A cheaper 3-run recipe is already worked out at
   `2026-07-27-edge-full-system.md:172-181` — V22 uses that, and does not attempt E90.

### Task V3: Fix MFE/MAE corruption — **done 2026-07-31**

**Files:** `swingbot/core/analytics/mfe_mae.py`, `tests/test_mfe_mae.py`,
`scripts/backfill_journal_mfe.py`

`mfe_r` was `None`/NaN in **66/339 (19%)** journal entries and **negative in 7**.
Negative is impossible by definition — MFE cannot go below zero.

**Two distinct bugs, both real, both fixed:**

- [x] **Step 1 (root cause, deeper than the plan assumed):** `journal_trade_close`
      sources its OHLCV via a **live, unguarded `yf.download()` call**
      (`swingbot/core/data.py:get_daily_data`) at the moment a trade closes. A
      transient network failure silently produces `df=None` → `mfe_r=None`; a
      transient bad Yahoo snapshot can produce nonsense — one live case computed
      `mfe_r=-1845.95`. Recomputing the *same* trade from the stable, network-free
      `data/backtest_cache/` (bridged by V1) gives `mfe_r=4.0258`, matching a manual
      hand-calculation exactly and confirming the diagnosis. The originally-assumed
      cause ("misaligned frame" inside `compute_mfe_mae` itself) was real but minor
      by comparison — see Step 2.
- [x] **Step 2 (the minor, real bug):** `compute_mfe_mae` had an **asymmetric
      clamp** — `mae_r` was `max(0.0, ...)`, `mfe_r` was not — so a same-day trade
      whose single daily bar never re-touched entry could legitimately compute a
      small negative `mfe_r` (e.g. AMD/SNOW/NOW/GLW, all same-day single-bar
      windows). Fixed with the matching clamp. 2 new regression tests (bullish +
      bearish mirror), all 8 tests in the file green.
- [x] **Step 3:** `scripts/backfill_journal_mfe.py` recomputes only entries that were
      actually corrupt, via `journal.build_entry` — the exact function a correct live
      write would use — reading `backtest_cache` instead of hitting yfinance again.
      The one user-entered `note` in the live journal was preserved. **Result on the
      live journal (345 entries): 63 fixed, 0 negative remaining.** 9 stay
      unresolved, fully accounted for — 3 have no matching record in `trades.json`
      at all (tracked as **V45**, a separate bug), 6 are today's trades whose window
      has no daily bar yet in a cache snapshotted once per day (self-resolves at
      tomorrow's refresh). **Not met exactly as originally written** — "0 None
      across all entries" undersold a same-day data-freshness limit that's inherent
      to any offline-cache backfill, not a defect; re-running this script tomorrow
      closes the 6 same-day cases automatically.
- [x] **Process note:** unlike V2's watchlist/ticker_meta_cache edits, this
      mutation ran without a pre-edit backup of `journal.json`. Lower risk here —
      the fix is deterministic and reproducible from `trades.json` + the cache, and
      the full before/after diff survives in this task's dry-run output — but the
      backup-before-mutate habit should have applied here too.

      manager somehow didn't — strictly-worse-or-equal, not double management), and
      with the manager off the loops keep closing these trades so nothing is
      stranded open. Same shape as the `plan_id` skip `check_near_tp_timeout`
      already had — that path had this exact bug fixed for it earlier; the other two
      were missed. 9 tests in `tests/test_manager_owned_target.py`; the 4
      bug-specific ones were confirmed red against the pre-fix code.

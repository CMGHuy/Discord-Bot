# Durable lifecycle notifications — implementation index

**Bump:** bot patch, ui patch
**Edge:** harvest
**Screen:** harvest-headroom docs/superpowers/results/2026-10-28-notification-delivery-evidence.md
**Spec:** [Approved v197 spec](../specs/2026-10-28-v197-durable-lifecycle-notifications.md)

**Goal:** Admin close and cancel currently risk losing their Discord notice between a state change, destructive queue drain and a failed send. This plan makes that delivery intent durable: an accepted admin action commits its state and immutable notification together, and the bot retains pending work until it records a Discord message acknowledgement. Operators can distinguish cancellation from closure, see backlog problems and recognize a duplicate by the same visible event ID.

The existing Postgres queue remains the single source of delivery work. Short transactions claim one event immediately before a bounded send; lease fencing protects acknowledgements and retries. Trading rules, fill calculations, issuance safety and automatic notification families keep their current behavior. Success is demonstrated by rollback, migration, concurrent claim, crash recovery, stale acknowledgement, rendering and UI regressions, followed by one full backend/frontend verification and a three-width layout audit. This is a delivery-integrity improvement, with no inferred trading-performance claim.

**Architecture:** Keep the physical `manual_close_notify` table and bigint infrastructure key. Add a pure event contract in `core/infra`, indexed queue state and explicit repository transitions. Add narrow caller-connection interfaces to account and manual trade persistence, then one admin orchestration module owning commit and post-commit hooks. A separate queue renderer and delivery worker return actual message IDs without changing the automatic-close sender. The existing operational health route and Scan tab display the queue projection.

**Tech stack:** Python, SQLAlchemy/Postgres, Alembic, discord.py, Flask, Angular and Vitest; no new paid service or external queue.

- Retry until delivered, at least once. Lease is 120 seconds; the entire resolve-and-send operation is bounded at 30 seconds. At most 20 claims per tick, one claim immediately before its send; never preclaim a batch.
- Retry delays: 5, 15, 60, 300, then 900 seconds forever; honor a longer numeric Discord `retry_after`. Blocked errors retry at 900 seconds. No retry ceiling or pending-record expiry.
- Missing destination, unavailable channel, permission denial and malformed snapshot remain durable and blocked. Do not catch a failed send and count it as acknowledged.
- Preserve seven days of acknowledged records, then prune only rows with a recorded message ID and delivery timestamp. Database failure after a send can repeat the same visible event ID.
- Resolve destination at enqueue. Never reread the current destination config during delivery. A configuration repair that changes channel ID requires explicit audited retargeting; that operation does not mutate the rendering payload or event ID.
- Manual trade/plan writes, account settlement/history and event insertion share one connection and one commit. No database error is swallowed on this transactional admin path. Legacy automatic callers retain existing behavior. Journal and snapshot hooks run only after successful commit, using committed trade snapshots; they are derived post-commit effects, not the authority for action success.
- Market data/override preparation occurs before acquiring database locks. Re-read and validate the current locked state before mutating. A pre-read or an in-process `_LOCK` is not cross-process exclusion.
- Lock order for these admin commands: transaction advisory account-settlement lock, plan row when present, trade row when present. Hold locks only through the database transaction. Serialize admin settlements before reading cumulative realized P&L; do not sum the newly closed row and then add it again.
- Schema promotion requires `register` tuple and `PROMOTION_REASONS`; retain document copies on migration/demotion. No read-time legacy shape upcasting. Old DELETE drain is removed from the new consumer.

## Frozen cross-task contracts

### Event and migration shape (V197-1)

`make_event` accepts keyword-only `transition_id: str`, `kind: str`, `target_channel_id: str | None`, `occurred_at: str`, `payload: dict`. It deep-copies payload and returns the canonical queue record; invalid new events raise ValueError. Use UUID5 with `uuid.NAMESPACE_URL` over `swingbot:lifecycle:{transition_id}:{kind}`. The transition UUID4 is created once under the producer's transaction and persisted on the trade as `manual_transition_id`, or in the appended plan history entry as `transition_id`. Retrying delivery never creates another identity; distinct committed transitions cannot collide on plan/status alone.

Queue flat record: `event_id`, `transition_id`, `kind` (`trade_closed` or `plan_transition`), `target_channel_id` (decimal string or null), `queued_at` (aware ISO timestamp), `payload`, `attempt_count` (initial 0), `next_attempt_at`, `lease_token`, `lease_owner`, `lease_until`, `last_error`, `blocked`, `delivered_message_id`, `delivered_at`, `retarget_history` (initial empty list). Tokens and times initialize null except next attempt equals queued time. Errors are bounded safe codes, not raw exception messages. The repository returns no infrastructure `id`; event_id is the public lookup identity.

Payload contains `ticker`, `direction`, `plan_id` (nullable), `trade_id` (nullable), `prior_status`, `new_status`, `reason`, `occurred_at`. A `trade_closed` payload also carries `trade`, a deep copy of the recorded closure dict with its renderer's existing `id` key inside the nested document. A plan CLOSED payload may carry `trade` when a linked trade was settled; CANCELLED must not carry a filled-trade result. Plan events without a linked trade still render as lifecycle transitions, with no invented fill or result. Trade payload includes recorded fields and leg results required by `build_closed_trade_embed`; do not synthesize them from a fresh quote at send time.

Promoted columns in addition to existing `queued_at`: `event_id` TEXT NOT NULL unique (lookup/deduplication index), `next_attempt_at` TIMESTAMPTZ NOT NULL (due selection), `lease_token` TEXT nullable (fenced updates), `lease_until` TIMESTAMPTZ nullable (reclaim selection), `delivered_at` TIMESTAMPTZ nullable (pending partial index and retention). Keep event kind, channel, attempts, blocked/error, payload, lease owner and message ID in JSONB. Add a partial pending due index on `(next_attempt_at, queued_at)` where delivered_at is null, and a partial delivered_at retention index. Register every promotion and reason. For mutations keep promoted copies consistent in doc so demotion loses no state.

Migration `v197_001` chains to the then-current sole head (brief observed `v173_002`, recheck after v194). Assign each legacy row a deterministic transition identity `legacy-manual-close-notify:{physical_id}` and its derived event ID once; normalize into the new shape, retaining the complete original document in `legacy_payload`. Existing explicit `plan_transition` stays that kind/status; other existing snapshots become `trade_closed`. Incomplete legacy snapshots are blocked with `legacy_snapshot_incomplete`, with no invented prior status, direction, fill or result. Their unknown fields remain null in payload, and runtime validation rejects them visibly until a separately reviewed data repair.

Legacy destination resolution occurs once at upgrade from explicit Alembic x argument `lifecycle_channel_id`; absent/invalid destination becomes null and blocked (`destination_unresolved`) instead of silently taking future config. Empty-table migrations need no argument. Missing historical fields remain unknown, never fetched from today's trades/plans. Preserve canonical event identity on a downgrade/re-upgrade; downgrade copies every promoted field back into doc before dropping only new indexes/columns, and does not delete any queue row. Upgrade recognizes its own preserved canonical document, never generates new IDs for it. This compatibility is confined to the revision, not runtime reads.

### Repository state transitions (V197-2)

All `now` arguments are timezone-aware datetime objects, required for deterministic tests; persistence returns normalized timestamp strings. `enqueue` inserts canonical events and never swallows failure. Duplicate same event_id with identical immutable kind/channel/payload is a no-op; a conflicting immutable snapshot raises ValueError, so uniqueness cannot conceal producer bugs.

`claim_one(owner: str, *, now, conn=None)` selects due, undelivered rows with no live lease using `FOR UPDATE SKIP LOCKED`, ordered by next_attempt_at then queued_at/event_id. It writes a fresh UUID token, owner and now+120-second expiry, increments attempts, and returns the updated record. Its internally owned transaction commits before returning. No network operation occurs while that transaction is open. Owner is process/tick identity; token is unique per claim.

`acknowledge` and `reschedule` require matching event ID/token, undelivered state and lease_until > now. Zero matched rows returns False and changes nothing. Acknowledgement stores nonempty Discord message ID and timestamp and clears lease/blocked/error; success is counted only when this write commits. Reschedule clears lease and writes next due, safe error code and blocked flag. It returns whether ownership was valid, not whether a message was sent. Only an accepted change from unblocked to blocked emits the required ERROR; a change of blocked cause is also a blocked state transition and emits ERROR. Include ID/kind/queue age and safe code, never raw payload/credentials.

`health` returns exactly `{pending_count: int, oldest_pending_age_seconds: float | None, blocked_count: int}`. Pending includes blocked and leased rows; delivered does not. Empty pending age is null; clamp negative age to zero. `prune_delivered` removes only rows older than seven days with both delivered_at and nonempty delivered_message_id. `pending` becomes the pending count, not total retained rows. Remove `drain` after consumer migration; no runtime compatibility deletion path remains.

`retarget(event_id: str, channel_id: str, *, actor: str, reason: str, now, conn=None)` requires nonempty actor/reason and valid decimal channel ID, refuses delivered or live-leased rows, and appends `{at, actor, reason, from_channel_id, to_channel_id}` to retarget_history within the same row-locked transaction. It resets due time to now, clears lease and destination-blocked state only; a malformed payload stays blocked. It emits a sanitized audit line after success. It is an explicit operator repository operation documented in V197-8, not an automatic configuration watcher or new admin endpoint.

### Atomic producer boundary (V197-3 and V197-4)

Account helpers add keyword-only conn and pass it all the way through `account_repo().load/save`, all `trades_repo().list_all` reads used for cumulative P&L and balance history writes. Caller-owned transaction settlement failures propagate. Preserve non-transactional automatic settlement's existing catch/log behavior. Avoid rewriting the sizing code. Serialize admin commands with a transaction advisory lock using fixed namespace/key `(197, 1)` before plan/trade locks; this also works when the account row has not yet been seeded.

`close_trade_manual_in_transaction` requires a supplied connection and an already resolved price or None (None means no quote is available; never make network calls inside). It locks/re-reads the trade row by trade_id, returns None if absent/not open, sets closed_at/transition identity, applies the existing price math, settles account and history strictly using the same connection, then persists the trade. Settlement precedes the final closed trade upsert so `apply_realized_pnl` reads prior realized totals and adds this trade once. Return the committed-intent snapshot, never mutate a shared cached fixture. This method does not call journal, snapshot refresh, or success logs. `after_manual_close_commit` calls existing `_after_close` and `_refresh_snapshot_safely` only after the outer commit. Existing `close_trade_manual` remains available to automatic/legacy callers.

PlanStore `get_record(plan_id, *, conn=None, for_update=False)` and `get` read one fresh repository row; for_update requires caller connection and locks that row. `update(plan, *, conn=None)` performs both existence check and write on conn. New transactional trade code uses the existing `_json_record`/`_db_upsert` conversions and repository table access; no new general-purpose repository locking abstraction is required.

The three admin service functions prepare quotes/override stamps before opening `transaction()`, acquire advisory lock and fresh row locks, validate legal status again, create and persist transition identity, write all state, then enqueue one event on that connection. Plan-close creates one plan_transition notice even with a linked trade, not two notices. Legacy-close creates one trade_closed notice. Pending cancel creates one CANCELLED plan_transition with no settlement. Plan history records prior/new status context and recorded time. Bulk uses one transaction per position and increments success only after commit; one position failure does not abort later positions.

`LifecycleNotFound` maps to existing 404 envelope, `LifecycleConflict` to existing 422 envelope, persistence failure to `error('unavailable', 'The action could not be saved. Try again.', 503)`. An enqueue/settlement/plan/trade write failure leaves every authoritative row unchanged and no hooks called. Post-commit derived hook failure retains the existing safe logging semantics and cannot turn a committed action into a misleading rollback response. Existing endpoint response projections stay intact. Do not leave `_queue_notify` swallowing exceptions as an alternate producer.

### Renderer and worker boundary (V197-5 and V197-6)

`build_lifecycle_notification` validates the immutable snapshot, delegates a trade snapshot to existing `build_closed_trade_embed`, and renders plan CLOSED/CANCELLED with separate explicit titles. CANCELLED describes an unfilled plan and never invokes closure-result rendering. All event variants include ticker, direction, IDs, prior/new status, reason and recorded transition time. Append `Event <event_id>` to the existing footer (preserve icon/chrome); use recorded transition time as the event timestamp. Preserve existing push kwargs/content conventions and recorded result values.

`send_lifecycle_notification` uses only target_channel_id from the event, resolves cached channel then fetches if necessary, awaits `channel.send(**ui.push_kwargs(embed))`, requires a nonempty message.id, and returns its string. It raises on failure; invalid snapshots/destinations/unavailable channels/permission failures become `BlockedDelivery` safe codes. Do not alter the old `notify_closed_trades` function or its re-exports. Worker wraps the entire coroutine in `asyncio.wait_for(..., timeout=30)`.

`deliver_lifecycle_tick(bot, *, repo=None, now=None)` defaults to `notify_queue_repo`; `now` is an optional zero-argument clock callable returning aware UTC datetime, evaluated again for every claim/completion. Count actual claims as attempted, committed acknowledgements as acknowledged, committed transient reschedules as retried, committed blocked reschedules as blocked. Categories do not overlap. A stale completion or failed acknowledgement updates none of the outcome counters. Log an acknowledgement-storage failure separately without raw exception text; preserve leased intent for expiration. CancelledError propagates so shutdown does not fake a delivery outcome. Per-event retry/reschedule failures are isolated; a global claim DB outage ends that tick safely.

Worker owner is a fresh tick UUID. It claims once, sends once, stores outcome, then claims the next event until empty or 20 attempted. Retry scheduling uses the persisted attempt_count (first failure → 5 seconds). Classify timeout/network errors as retryable, explicit blocked causes as capped retries. A longer numeric retry_after overrides the retry delay, including blocked interval where provided. Housekeeping prune runs once per tick with isolated failure reporting. The old `_take_manual_close_queue` destructive adapter and optimistic 'Posted N' log disappear; `config_watcher` keeps its current cadence and automatic monitor paths remain separate.

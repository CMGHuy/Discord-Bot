# v67 — JSON to PostgreSQL Implementation Plan (index)

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Version:** ui 1.9.2 · bot 1.5.0
**Bump:** bot minor (1.5.0 → 1.6.0) · ui patch (1.9.2 → 1.9.3)
**Edge:** none (integrity)

**Goal:** Replace the `data/*.json` persistence layer with PostgreSQL while
keeping schema change as cheap as editing a Python dict.

**Architecture:** A hybrid schema — stable, queried fields become typed
columns; everything else lives in a `doc JSONB` column, joined and split by a
codec so call sites keep their flat-dict contract. Existing store classes
(`TradeLog`, `PlanStore`, …) keep their names and public methods; only their
bodies swap file I/O for repository calls. Migration is a store-by-store
strangler driven by a `DB_STORES=name:stage` mapping, so every step is
independently reversible.

**Tech Stack:** PostgreSQL 18 (`postgres:18-alpine`), SQLAlchemy Core,
psycopg 3, Alembic, pytest.

**Spec:** `docs/superpowers/specs/2026-08-29-v67-json-to-postgres-design.md`

## Global Constraints

Every task's requirements implicitly include this section.

- **PostgreSQL 18** (`postgres:18-alpine`), pinned exactly. One added container.
- **SQLAlchemy Core only — no ORM.** Repositories return plain `dict`s, never
  model objects. Call sites keep the dict contract they have today.
- **Repositories never leak SQL upward.** Store classes call repositories;
  nothing outside `swingbot/core/db/` imports SQLAlchemy.
- **Every table gets `doc JSONB NOT NULL DEFAULT '{}'::jsonb` and
  `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`.** Promoted columns are the
  exception, not the rule — promote only a field that is filtered/sorted in a
  hot path, needs a `NOT NULL`/`CHECK`, or is a foreign key.
- **Fail fast.** A write that cannot reach Postgres raises. Never swallow a
  write error; never fall back to a file for trading state. Regenerable caches
  (`rs_cache`, `ticker_meta_cache`) may fall back to recomputation on *read*.
- **No behavior change.** Analytics outputs must be numerically identical
  before and after. SQL pushdown is explicitly out of scope for this plan.
- **`requirements.txt` pins exactly** (`==`), never a `>=` floor, and every new
  dependency gets a comment explaining why it is there — match the file's
  existing style.
- **Alembic revisions use explicit part-prefixed ids** (`alembic revision
  --rev-id p3_004`), never autogenerated hashes. One head at all times.
- **Per-task verification is narrow:**
  `python scripts/dev/testrun.py file tests/<the one file this task touched>.py`
  (~7s), or `... fast` (~27s) only when the blast radius genuinely crosses
  files. **Never `... full` per task** — that is the plan's final task only.
- **Files that stay as files, and must not be migrated:** `market_data/`,
  `data/backtest_cache/*.csv`, `exports/`, `validation_registry.json`,
  `sp500.json`, `etfs.json`, `.env`, `.env.bak`, `data/admin_session_secret`,
  `VERSION.json`.

## Schema evolution is a first-class requirement

The spec names two reasons for this work, and only one of them is the lost-update
bug. The other is churn: `v39`, `v50`, `v52` and `v58` each reshaped the trade or
plan record, so **the data model changes roughly once per plan**, and any design
needing a migration per field change is the wrong design here.

That is a requirement this plan has to keep meeting after it ships, not a
property it can claim once. The four operations and what each costs:

| Operation | Cost | Migration? |
|---|---|---|
| **Add a field** | `record["gamma_flip"] = x` | **No.** Queryable immediately as `doc->>'gamma_flip'` |
| **Rename a doc field** | one `UPDATE ... SET doc = doc - old \|\| ...` | **No** |
| **Drop a doc field** | one `UPDATE ... SET doc = doc - 'name'` | **No** |
| **Promote a doc field to a column** | `ADD COLUMN` + backfill + one name in `PROMOTED` | Yes — **and no call site changes**, because they never read columns directly |

Part 8 exists to make those four real rather than asserted: a documented recipe,
a promotion tool exercised end-to-end, and tests that fail if the property
erodes. Do not treat Part 8 as optional polish — a plan that delivers the
lost-update fix and loses the schema flexibility has traded one of the spec's
two reasons for the other.

## The five-stage strangler

Every migrated store moves through the same stages, selected per store by
`DB_STORES` (a comma-separated `name:stage` mapping; unlisted stores default
to `json`):

| Stage | Meaning |
|---|---|
| `json` | Files only — today's behavior |
| `dual` | Write both, read files. Divergence is logged, not raised |
| `db` | Postgres only |

A store rolls back one stage by editing `DB_STORES` and reloading — no
redeploy. Deleting the JSON code path happens only in Part 6, after every
store has run at `db` in production.

## Parallelisation

The rule this repo enforces: two tasks may share a group only if they touch
**disjoint files** *and* neither consumes a symbol the other introduces.
Concurrent sessions share this working tree, so a wrong grouping silently
overwrites work rather than conflicting.

- **Sequential: Part 1 before everything.** It introduces `codec.py`,
  `schema.py`, `engine.py`, the `DB_STORES` resolver and the test fixtures that
  every later task consumes. This is a contract dependency, not an ordering
  preference.
- **Parts 2–5 may run concurrently with each other**, one part per session or
  worktree. Each owns a disjoint set of store modules and its own Alembic
  revision prefix. **Within a part, tasks are sequential unless that part's own
  `## Parallelisation` section says otherwise.**
- **Sequential: Part 3's watcher rewrite (P3-19…P3-24) lands after every
  operational store in Part 3**, because its tests assert against tables those
  earlier tasks create.
- **Sequential: Part 6 after all of 2–5.** Cutover cannot precede the stores it
  cuts over, and dead-path deletion needs every reader already migrated.
- **Sequential: Part 7 after P6-07** (the production stage flip) — a snapshot
  pull needs production to actually be on Postgres. In practice run it after
  P6-11, so the docs sweep and the local-dev guide land together.
- **Group 7/8 (parallel):** Part 7 and Part 8 — disjoint files
  (`profiles.py`/`datasets.py`/`scripts/ops/` versus `codec.py` tests and
  `scripts/db/promote_field.py`), and neither consumes a symbol the other
  introduces. Part 8's only hard dependency is Part 1's codec.
- **Sequential: P6-12 last, after Parts 7 and 8.** It is the plan's single
  full-suite gate, the version bump and the close-out, and it has to cover
  every part's code — including these two. Numbering is not execution order.
- **Alembic is the one cross-part hazard.** Parts 2–5 running concurrently each
  generate revisions. Prefixes are reserved here — Part 1 `p1_*`, Part 2
  `p2_*`, Part 3 `p3_*`, Part 4 `p4_*`, Part 5 `p5_*`, Part 6 `p6_*`, Part 7
  `p7_*`, Part 8 `p8_*` — so a collision surfaces as a name clash, not a silent
  branch. P6-01 asserts `alembic heads` returns exactly one. A real branch is
  resolved with a merge revision, **never** by editing a `down_revision` that
  has already run.

## Verification cadence

Per task: the narrow run named in that task. **Not** the full suite.

The plan verifies itself **once**, as P6-12 — which runs **last**, after Parts
7 and 8, so that one run covers every part's code:

```bash
python scripts/dev/testrun.py full     # expect 0 failed, 0 xfailed
cd frontend && npm test                # only if any part touched frontend/
```

A red result there is the start of the work, not a reason to re-litigate
earlier tasks — fix forward from the failures the run names.

## Success criteria

Copied from the spec so an executor never has to open it to know when this is
done:

1. Every store in the spec's inventory reads and writes Postgres; no code path
   reads the migrated JSON files.
2. Imported production data matches its JSON source exactly — equal row counts
   and equal per-record checksums.
3. Analytics outputs are numerically identical before and after.
4. `python scripts/dev/testrun.py full` is green — `0 failed`, `0 xfailed`.
5. The SSE stream delivers the same event names with no SPA change.
6. A restore from `pg_dump` into an empty database has been performed and
   verified once.
7. Two concurrent writers (bot + admin) cannot lose an update — proven by a
   regression test that **fails against the current file-based stores**.

Three more this plan adds, which the spec implies but does not list:

8. A production snapshot pulls to a local database with one command, and
   production is readable live from a dev machine through a role Postgres
   itself refuses writes from (Part 7).
9. No committed file points `DATABASE_URL` at production (Part 7).
10. Adding, renaming and dropping a record field all cost **zero migrations**,
    and promoting one to a column changes **no call site** — each demonstrated
    end-to-end, not asserted (Part 8).

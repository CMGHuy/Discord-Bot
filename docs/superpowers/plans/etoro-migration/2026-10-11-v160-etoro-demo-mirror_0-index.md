**Goal:** Every main-ledger plan the bot fills on paper is also traded, automatically, on the partner's eToro **demo** account; every order, fill and close is recorded in a new `broker_orders` table so a read-only parity report can show paper R against eToro R (gross and net), entry drift and skip counts.

**Architecture:** `swingbot/core/broker/` (created by v159 with `guard.py` only) gains five modules. `sizing.py`, `checks.py` and `mirror.py` are pure: the plan's own size scaled down to `ETORO_MAX_TRADE_USD`, every order-risk check, and the `PlanEvent` → `BrokerAction` translator. `etoro_client.py` is a thin `requests` client with a 10 s timeout and a non-sleeping 15-per-60 s token bucket over the shared order budget, demo routes only. `executor.py` turns actions into `broker_orders` rows ("no row, no send"), sends them in per-plan `seq` order under a 20 s budget, looks up in-flight orders, persists close-time P&L and runs a once-a-day reconciliation. `broker.mirror_events` is the one entry point; `trade_monitor` calls it after `_post_plan_events` inside `asyncio.wait_for(..., MIRROR_TICK_BUDGET_S)`. Three scripts (parity report, drain, smoke) read the table or reuse the client.

**Tech Stack:** Python 3.11, `requests` (exact pin), SQLAlchemy + Alembic on Postgres, pytest via `scripts/dev/testrun.py`, discord.py `tasks.loop` (the hook site only).

## Global Constraints

- **Demo only, never `account: real`.** Only demo route paths are written anywhere (the read-only market-data rates route has no account). `etoro_client.EtoroClient.__init__` and `executor.Executor.run_tick` call `guard.assert_demo("demo")`; so do both ops scripts (`main()`), because v159's AST scan fails any module under `swingbot/`, `scripts/`, `bot.py`, `admin_ui.py` that imports a module whose dotted name contains `etoro`, has a string containing `etoro.com`, or reads `ETORO_USER_KEY`/`ETORO_API_KEY` without calling `assert_demo`. Never set `ETORO_ALLOW_REAL`/`ETORO_REAL_SIGNOFF` in any `.env*`.
- **There is no `validate_order`, `BrokerOrder`, `OpenBook`, `pre_open.py`, `ETORO_MAX_TRADE_EUR`, `ETORO_ACCOUNT_SIZE` or `ETORO_RISK_PCT`.** v160 owns sizing (`sizing.py`) and every order-risk check (`checks.py`), partner decision 2026-10-11. Where v159's text says `pre_open.py`, read `checks.py`.
- **Settings (EM1), section `"eToro Paper Trading"`, hot-reloaded, read as `config.<ATTR>` at call time, never cached:** `ETORO_MIRROR_ENABLED` (checkbox, default `"false"`), `ETORO_MAX_TRADE_USD` (float, default `"100"`, `min=0`). `ETORO_MAX_TRADE_USD <= 0` skips every open with `no_trade_cap`. No other new setting.
- **Sizing:** `plan_units = planning.account.compute_position_size(entry, plan.stop_loss)["shares"]` and the sizing balance is that call's `["balance"]`; `sizing.mirror_units` only ever scales **down**. Entry, stop and target are never changed. `None` from `compute_position_size` skips with `zero_units`.
- **Units precision:** `whole` → 0 decimals, `fractional` → `sizing.FRACTIONAL_UNIT_DECIMALS = 4` (eligibility's `unitsQuantityType`). **Rate precision:** eToro publishes none; `mirror.round_rate(rate)` rounds to 2 decimals at or above 1.00 and 4 below (US tick sizes).
- **eToro routes, verified 2026-10-11 against the catalog v1.387.0 (`get-all-routes`/`get-route-spec` over `https://mcp.public-api.etoro.com`); host `https://public-api.etoro.com` (answers 401 unauthenticated on `/api/v1/me`).** These exact strings are the only paths in `etoro_client.py`:

  Headers on every request: `x-user-key` (`config.ETORO_USER_KEY`), `x-api-key` (`config.ETORO_API_KEY`), `x-request-id`, never `Authorization`.
- **Lookup status ids** (`GetOrderInfoStatus.id`): 3 Filled, 5 PartiallyFilled, 9 CanceledPartiallyFilled → `filled`; 4 Rejected, 7 Canceled, 8 Expired, 10 RejectedPartiallyFilled → `rejected`; 1, 2, 6, 11, 12 → still `in_flight`. 6/7/8/9 are not in the spec's list; this mapping is the plan's (final means final, units recorded when any filled).
- **A `move_stop` has nothing to look up** (the PATCH returns only an `operationId`): 202 → `filled` at once; the daily reconciliation catches a stop eToro did not apply. Close orders are looked up by `referenceId` like opens.
- **`no_position`** is an executor skip reason beyond the spec's open-check table: a `close_units`/`close_all`/`move_stop` row whose plan's `open` row ended `rejected` or `skipped` is marked `skipped` with `skip_reason = "no_position"` and never sent.
- **Idempotency:** `request_id = str(uuid.uuid5(executor.NAMESPACE, f"{plan_id}:{action}:{event_key}"))` with the fixed `NAMESPACE = uuid.UUID("5b0c1f0e-7a4d-5c2b-9e61-3d8f2a6c1e47")`, never changed once shipped. `event_key`: `"filled"` (open), `"closed"` (close_all), `"tp1_partial"` (close_units), `f"{target:.4f}"` (move_stop), `"drain"` (the drain script's close_all).
- **Never `StoreWriteHalt`.** A failed mirror write is classified with `core.db.write_failure.is_store_write_failure(exc)` and logged at WARNING; the action is not sent.
- **Logging contract:** each skip logs one INFO line starting `etoro mirror skipped (<reason>): <ticker> <plan_id>`; each sent action and each final outcome logs one INFO line starting `etoro mirror <action> <status>: <ticker> <plan_id>`; widen drops and reconciliation mismatches log WARNING. Nothing goes to Discord.

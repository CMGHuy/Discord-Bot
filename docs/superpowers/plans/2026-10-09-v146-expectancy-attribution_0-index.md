**Edge:** none (integrity)

**Spec:** [`docs/superpowers/specs/2026-10-09-v146-expectancy-attribution-design.md`](../specs/2026-10-09-v146-expectancy-attribution-design.md)

**Goal:** Measure once, on the live book and on TRAIN side by side, whether today's confidence score (or any factor inside it) ranks trades by realised expectancy, and record a pre-registered PREDICTIVE / WEAK / NOT PREDICTIVE verdict.

**Architecture:** Four instrument changes make the inputs exist: numeric per-factor `confidence_points` on every scored trade and plan (I1, with a one-off Alembic backfill parsing the old text), a populated `risk_features.days_to_earnings` (I2), per-trade TRAIN rows from the confluence replay carrying a confidence score computed exactly as live (I3), and two new Analytics breakdown dimensions (I4). A pure study module, `swingbot/core/analytics/expectancy_attribution.py`, buckets each population, computes week-clustered bootstrap CIs, BH q-values over every look and the verdict; a light store module under `swingbot/core/infra/` owns the atomic JSON file and the `load_latest()` loader v150 imports. Nothing changes what any user sees in an alert: every change is a recorded field or a read-side grouping.

**Tech Stack:** Python 3.11, pandas/numpy, SQLAlchemy + Alembic on Postgres, pytest; Angular (one dropdown list), Vitest.

## Global Constraints

- **No alert, gate, level, size or exit changes for any user.** The only scorer change outside recording is the TRAIN-only `neutral_expectancy` switch, default `False`; every live caller keeps today's behaviour byte for byte.
- **VALIDATION is never read.** TRAIN only (`--train`), confluence replay (`--scenarios`), `--exit-model v2 --scale-out`.
- **Populations are never pooled.** Live and TRAIN are computed, bucketed and reported separately; no figure combines them.
- **Buckets with N < 30 carry `thin: true` and enter no verdict.** `THIN_N = 30` in the study module. `aggregate.MIN_CELL_N` (20) is untouched.
- **No reader ever parses `confidence_breakdown` text.** The parser lives only in the `v146_001` revision; tests load it from that file.
- **No-lookahead:** every I3 field is computed on `window = df.iloc[:i+1]` and SPY sliced to the signal bar's timestamp; truncating the frame after the signal bar changes none of them.
- **Tied scores are never split.** A tied block goes wholly to the bin containing its median rank; no randomness anywhere except the recorded bootstrap seed.
- **Tercile cut points are fixed once on the full sample**, never recomputed per bootstrap resample.
- **R is net of frictions** in both populations (`swingbot/core/edge/frictions.py`); gross ExpR is reported beside net.
- **The verdict is computed once** (V146-14) and carried forward unchanged in `verdict_of_record`; later runs are descriptive.
- **The cheap loader:** `load_latest()` is importable without `pandas`, `numpy` or `swingbot.core.backtesting` in `sys.modules`.
- **The name shown everywhere is "Expectancy attribution".**
- Every function written or changed ends below cyclomatic complexity 15 (`python -m radon cc -s -n C <files>`). Legacy functions already >= 15 never get worse: `_score_confidence_legacy` E40, `TradeLog.log_trade` C15, `replay_scenarios` C15, `run_scenario_mode` C19, `run_backtest_range.main` F65.
- Per-task verification is the narrow run: `python scripts/dev/testrun.py file <test>` (or `cd frontend && npm test -- --include <spec> --watch=false`). The full suite runs once, in V146-15.

## Handoff

Deviations from the spec and decisions taken while writing this plan. Each is final for every part.

1. **Alembic head is `v144_001`, not `v116_002`.** The new revision's `down_revision` is the live head; V146-3 re-checks it with `alembic heads` before writing the file.
2. **Legacy complexity.** `_score_confidence_legacy` (E40), `TradeLog.log_trade` (C15), `run_scenario_mode` (C19), `replay_scenarios` (C15) and `run_backtest_range.main` (F65) are already >= 15. All new logic goes into named helpers; each task's last step re-measures the touched functions and none may score higher than before.
3. **`replay_scenarios` keeps its `(i, plan)` return.** Twenty callers (scripts and tests) unpack it as a 2-tuple. Instead of widening it, V146-7 moves the body into a new `replay_scenarios_detailed(...) -> list[ReplayHit]` (split into helpers below 15) and `replay_scenarios` becomes a one-line projection of it. `ReplayHit` carries `scenario` and `target_confluence`, which I3 needs.
4. **SPY reaches the replay workers through a new task-tuple slot.** `run_scenario_backtest(..., spy_df=None, collect_rows=False)` appends `spy_df` as `args[10]`; only `_replay_ticker_rows` reads it. `_replay_ticker`'s dict return (pinned by `tests/scripts/test_training_universe.py`) is unchanged.
5. **Live `r_multiple` and frictions are unverified.** `metrics.r_multiple` contains no friction code; whether live fill prices already include slippage is checked as an explicit step of V146-12 (the task that consumes it). Decision rule, from the spec: the study's R is net of frictions. If live fills are not friction-adjusted, the study applies the same `apply_frictions` + `commission_r` model to live rows as to TRAIN rows; if they are, it uses `r_multiple` as is. Either way the step records which, and the results doc states it.
6. **The loader lives in a light module.** `import swingbot.core.analytics` already loads `pandas` and `numpy` (measured 2026-10-10: the package `__init__` imports metrics, calibration, journal and more), so no function inside that package can satisfy the cheap-import requirement. `load_latest()` and `write_latest()` live in `swingbot/core/infra/expectancy_attribution_store.py` (stdlib + `swingbot.config` + `swingbot.core.infra.jsonio` only; `swingbot.core.infra` and `swingbot.config` measured light). `expectancy_attribution.py` re-exports `load_latest`, so the spec's "the module exposes `load_latest()`" also holds. The atomic write is `jsonio.atomic_write_json` (temp file + `os.replace`, with the Windows retry). **v150's gate must grep `swingbot/core/infra/expectancy_attribution_store.py` and `swingbot/core/infra/jsonio.py`**, and v150's `_load_attribution` imports the store module (v150 index § Blocked tasks already allows that substitution).
7. **`ConfidenceResult` attributes are `points` and `unevaluated`;** the stored record and plan fields are `confidence_points` and `confidence_unevaluated`.
8. **The live verdict run uses a scratch copy of the production `trades` table.** The live book is on the Hetzner VM and its rows need the `v146_001` backfill before the study can read factor points, but the revision only reaches production after merge. V146-14 exports the closed rows read-only, loads them into a scratch database on the local Compose test Postgres (`127.0.0.1:55432`), runs `alembic upgrade head` there (the real revision on real data: its parsed/skipped/unparsed counts are recorded), and runs the study with `DATABASE_URL` pointing at the scratch database. The scratch database is dropped afterwards. Production is never written. *Partner confirmed 2026-10-10: local copy of the production rows, before merge — not a run on the VM after deploy.*
9. **`verdict_of_record.n`** is the number of rows that entered the verdict: live monotonicity `n` plus TRAIN monotonicity `n`.
10. **`rs_quintile_label` is public** in `aggregate.py` (V146-6) so the study module (V146-10) buckets RS exactly as the Analytics dimension does.
11. **The closed table gets a v146 row** in `docs/claude/backtest-methodology.md` and `v146` joins `EXEMPT` in `tests/backtesting/test_preregistration_ledger_file.py` (the v143 precedent), in V146-14.
12. **TRAIN replay output path:** `data/reports/v146-train-scenarios.jsonl` (gitignored `data/`); the results doc records its row count and sha256.

# Fibonacci impulse-leg instrument and anchor diagnostic — implementation plan

> **For agentic workers:** Use the repo's `task-brief` and one-task implement/review cycle (superpowers:subagent-driven-development). Steps use `- [ ]` for tracking; read the spec with the task.

**Goal:** Build a causal impulse-leg instrument (`swingbot/core/market/fib_leg.py`) and a read-only diagnostic script (entries 2015-01-01..2025-12-31) that measures, against today's rolling-anchor Fibonacci trades, whether each of the handbook's four claims shows any signal. The output gates nothing.
**Architecture:** `fib_leg.py` is pure and has no live caller. It draws the leg from v121's `structure.confirmed_pivots` (origin) and `structure.pivot_confirmations` (the swing before the origin), works in a direction-oriented space so one code path serves bullish and bearish, and exposes `impulse_leg` (every bar) plus `leg_at` (last bar only, used by the script). `scripts/backtest/measure_fib_anchor_diagnostic.py` reuses v103's reference-arm collector (`measure_fib_v103.collect_trades("A", ..., 0.0, ...)`) for the Fibonacci trades, mirrors `ConfluenceEngine.run_ticker` for the confluence trades, stamps arm features from `df.iloc[:t+1]`, and writes bucket tables plus exit-rule verdicts.
**Tech Stack:** Python 3.11, pandas/numpy, existing `market.indicators.atr`, `market.levels`, `backtesting.backtest_scenarios`, the `scripts/backtest/funnel.py` pooled-stats helpers, pytest.

- Out of scope: any change to `fibonacci_entries`, `levels.py`, plans, alerts, charts, config flags, stored records, `structure.py` or `VERSION.json`. `fib_leg.py` is imported by no module under `swingbot/`, by `bot.py` or by `admin_ui.py`. Task V124-1 adds a test that enforces this.
- `fib_leg.py` adds no pivot detection. Origin = `confirmed_pivots(df, k=origin_k)["last_sl_pos"]` (bullish) / `["last_sh_pos"]` (bearish). The swing before the origin comes from `pivot_confirmations(df, origin_k)` flags converted to positions (`flatnonzero(flags) - k`). That is a lookup on v121's output, not a second detector, so `structure.py` needs no new accessor (the spec's "if needed" case does not arise).
- Frozen constants, copied from the spec: `origin_k = max(3, fib_lookback // 6)` (`ORIGIN_DIVISOR = 6`, `MIN_ORIGIN_K = 3`); end age `>= 3` bars (`MIN_END_AGE = 3`); ratios `0.382 / 0.5 / 0.618`; one tolerance `TOL_ATR = 0.25` shared by arms 1, 2 and 4; leg-dependent splits also at divisors `4` and `8`. Changing any of these needs a new spec.
- NO-LOOKAHEAD: every feature at entry bar `t` is computed from `df.iloc[:t+1]`. `impulse_leg` row `t` equals the last row of `impulse_leg(df.iloc[:t+1])`. A truncation test pins this.
- Windows (partner decision, 2026-10-02). **Diagnostic:** `DIAG_WINDOW = ("2015-01-01", "2025-12-31")` bounds entry dates and features. Extended cache `data/backtest_cache_ext`, v103 universe (the watchlist `_load_frames(None, None)` loads). Bars before 2015 serve only as lookback history. Every diagnostic collector and every diagnostic payload refuses a window starting before 2015-01-01 or ending after 2025-12-31. **Reproduction:** `REPRO_WINDOW = TRAIN_EXT = ("2010-01-01", "2023-12-31")`, exactly, and nothing else. The 2015/2025 bounds apply to the diagnostic window only. A trade entered by 2025-12-31 and still open then may resolve on 2026 bars: outcome resolution only, as the harness already does (`arms/windows.py`: "Exit simulation may walk past the window end"). No feature, bucket or verdict reads a bar after the entry bar, and no 2026 entry is kept. 2026 is the holdout (v104/v113 precedent). v103 already spent Fibonacci's 2024–25 VALIDATION shot (bullish `b=0.1`, FAIL). This diagnostic spends no budget, and every follow-on arm must name its own holdout.
- Reproduction gate: `collect-repro` runs the same v103 collector on `REPRO_WINDOW`, without features. Bullish must give N=815, WR 36.81%, ExpR +0.2219, universe 73 (v103/v102 reference `b=0`, compared at 2 dp for WR and 4 dp for ExpR). The bearish reference, N=169, WR 23.67%, ExpR −0.1269, is reported as description. A bullish mismatch must be explained in a committed note before `report` will write any bucket table.
- Exit rule, verbatim: "An arm proceeds to its own spec only if, on the bullish side, the favourable bucket has a higher win rate **and** an ExpR no lower than the rest, with N ≥ 30 in each bucket. Arms 1, 2 and 4 must also keep the win-rate sign at two of the three divisors." N here is `pooled()["n"]`, the decided (win + loss) count, which is the repo's `MIN_N_TRAIN` convention.
- Bearish rows are description only. No selection from "also described" columns. No re-run of a closed pre-registration's candidate cell: the v103 `b=0` reference arm is reproduced only as the baseline.
- Every function written stays below cyclomatic complexity 15 (`python -m radon cc -s -n C <files>`). Each task runs only its own test file (`python scripts/dev/testrun.py file <path>`). The full suite runs once, in Task V124-7. The measurement run comes after the plan (see "After the plan").

Overlap with v121/v122/v123: v121's `structure.pullback_legs(df, direction, k=3)` returns `(base, turn, t)` where `turn` is the last confirmed k=3 swing high. This spec's leg is different on purpose: its origin has strength `origin_k` (3 to 63), and its end is the highest High since the origin, not a pivot. So `fib_leg.py` reuses v121's pivot functions and not `pullback_legs`. v122 and v123 define no leg helper of their own; they consume v121's.

**Arm 4 identification route (the spec's Group 1 check, done read-only while writing this plan).** `replay_scenarios` yields `(index, plan)`. The plan does not carry the scenario's `stop_sources`/`target_sources`. The level map behind it can still be rebuilt exactly. `levels_asof` caches per `(ticker, horizon, index // 5)`, and the replay visits bars in order, so the map used at `index` was built at bar `max(MIN_BARS[h], (index // 5) * 5)`. The replay then re-splits that map against `Close[index]`. The scenario's stop level is the nearest level on the stop side, and its target-1 level is the nearest on the target side. The rebuild is verified per trade: the plan's `stop_loss` must equal `_clamp_stop_to_hard_cap(trigger_price, stop_level.price, is_bull)`. The Fibonacci candidates behind the trade are the Fibonacci-family labels in those two levels (the same two `primary_strategy_for` reads). Their prices come from `collect_candidate_levels` re-run on the map's own bar. The map bar is the frame that actually produced the level and is `<= index`, so it is causal. These three rules (map-bar recompute, stop + TP1 as "the level", all-or-nothing rebuild) are partner decisions written into the spec (§ The diagnostic, 2026-10-02). If any confluence trade fails the rebuild, arm 4 is reported as **not measurable with this instrument**. Task V124-5 ends with a one-ticker smoke run that prints only identification counts.

## Review focus

1. A NaN bar inside a leg, or a frame too short for any pivot, must give an all-NaN row and never raise. Task V124-1 tests a NaN bar, lengths 0/1/2/5/9 and a flat frame.
2. Equal highs at the leg's top must pick the **first** bar as the end, which can leave the leg undefined for one more bar. Task V124-1's tie test fails under last-occurrence.
3. An entry bar with fewer than `fib_lookback` bars of history has no rolling anchor. Arm 1 must put it in "rest" and the fractal flag must read `None`, with no raise. Task V124-4 tests `rolling_anchor` on a short prefix and `anchored_split(None, ...)`.
4. A bucket whose trades are all scratches/timeouts has `win_rate None`. The verdict must read it as "does not pass", not raise a `TypeError`. Task V124-3 tests it.
5. A confluence trade whose rebuilt stop level does not match the plan's stop, or that has no level on one side, must count as unidentified and make arm 4 "not measurable", never silently drop out. Tasks V124-5 and V124-6 test both.

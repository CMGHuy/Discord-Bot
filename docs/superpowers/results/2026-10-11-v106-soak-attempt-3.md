## Diagnosis (telemetry only; no code changed)

- **(c) is razor-edge by construction.** The baseline 0.01299 is exactly one
  skip per 77-ticker scan (CRWV's standing data-quality skip). Thursday had
  182 vs 180 -- two extra skips in 180 scans decided the clause. Alpaca did
  not cause it; it is not a latency signal.
- **(a) is an in-session slowdown that began Wed 10-07 afternoon**, not an
  Alpaca-side one: cold chunk median ~1.0 s (Mon/Tue) -> ~1.9 s (Thu/Fri),
  p95 2.7 -> 4-6 s, 15:00-17:00 UTC worst. Pre-open hours stay 0.9 s.
  - Flat across minute-of-hour: not restic (:07), not market_data_refresh (:02).
  - Not admin tape polling: 10-05 had 2916 tape requests and passed; 10-08 had
    73 and was the worst.
  - Median in-session phases (13-20 UTC): live_prices 6.5 -> 7.0 s and
    enrichment 9.9 -> 9.8 s flat, while crawl 15.0 -> 35.8 s and analysis
    72 -> 98 s (Fri) and scan duration 108 -> 153 s. The whole scan slowed,
    including pure-CPU analysis -- consistent with CPU contention on the
    2 vCPU VM rather than Alpaca network latency.
  - Timing lines up with bot 2.1.0 / 2.2.0 deploys (10-07 13:19 / 14:05 UTC)
    and 2.2.2 (10-08 12:09), but the cause is not proven.
- **Silent design fact:** every in-session scan cold-fetches 2y x 75 symbols
  ("0 from cache, 75 fetched") because the daily cache is older than
  SCAN_CACHE_MAX_AGE_HOURS (6 h) all session. A delta fetch spliced under the
  cache is possible (`history_splice.py` already exists) but refuses on any
  adjustment-basis mismatch and then silently drops depth -- not a safe
  blind fix.

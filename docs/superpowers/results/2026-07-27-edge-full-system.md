## Task E90: Full-system permutation test — NOT run, genuinely infeasible at n=200

The brief's command:

```
python scripts/permutation_test.py --component-json "$(cat docs/superpowers/results/adopted_components.json)" --n 200
```

resolves to `--component-json '{}'`. Reading `permutation_test.py`'s own
code (not assumed from the brief): with an empty component-json, this is
NOT a no-op the way "test a component when none are adopted" might
suggest — `_fold_run_fn` calls `run_folds({})` once per permutation, and
with `overrides={}` both "baseline" and "component" inside `run_folds` are
the same unmodified system, entry-shifted by a random offset via
`bt.ENTRY_SHIFT` (a pure array roll, zero cost difference per shift). So
this genuinely tests **whether the current baseline system's own pooled
expectancy is distinguishable from random entry timing** — a real,
meaningful question, not a moot one. This supersedes an earlier session's
different (and narrower) conclusion that permutation testing was N/A here
"because nothing is adopted" — the tool's *default* invocation with an
empty component-json still answers a real question about the baseline
itself.

**Why it wasn't run anyway: the arithmetic doesn't work.** Each call to
`run_folds(...)` inside `_fold_run_fn`'s `run(shift)` costs the same as
one full `--full` fold-table run — Run 2 above, still running as this was
written, had already spent **2+ hours of wall-clock / ~6700s of CPU** on
exactly that single computation before finishing. `--n 200` means **201
such calls** (1 real + 200 permuted). At even a conservative ~90-120
minutes per call, that's **300+ hours of continuous compute** for the
default sample size — not a "let it run overnight" job, a multi-week one
on this hardware. Even `--n 5` (nowhere near enough for a real p-value:
`p_value` is a fraction of 5 comparisons, useless resolution) would still
be 6 sequential multi-hour runs.

**This is not a "nothing to test" gap like E41/E42's — it's a real,
currently-unrunnable tool.** For permutation testing to ever be practical
against the full watchlist-scale system, either (a) `run_folds`/
`_default_run` needs a cheap-enough execution path for repeated
permutation calls (a much smaller ticker/strategy subset scoped
specifically for permutation testing, result caching across shifts, or
parallelizing the 200 calls across cores), or (b) a future component
adoption should be permutation-tested on its own narrower scope (the
original E41/E42 use case: one component, not the whole 78-ticker x
11-strategy x 10-horizon grid) rather than the unscoped full-system
default. Neither exists today. Flagging rather than either faking a
result or burning a genuinely multi-week compute budget on this machine
without asking first.

## Task E91: Sensitivity table — NOT run, both a real tooling gap and the same infeasibility as E90

The brief's command:

```
for bps in 5 10 20; do
  python scripts/wf_run.py --full --portfolio --component-json "{\"SLIPPAGE_BPS\": $bps}"
done
```

**Tooling gap (found by reading `wf_run.py`'s `main()`, not assumed):**
`--full --portfolio` together do not compose the way this implies. The
`if args.portfolio:` branch in `main()` runs `collect_portfolio_signals`
and `return`s *before* the `overrides = {} if args.full else
json.loads(args.component_json)` line ever executes. `collect_portfolio_
signals(start, end, strategies=None, horizons=None)` itself has no
`overrides` parameter at all — it hardcodes `frictions=True,
exit_model="v2", scale_out=True, tp2_mode="levels"` inside its call to
`run_backtest_daterange`, matching the E22 friction-adjusted baseline
exactly, with `SLIPPAGE_BPS` never threaded through. So `--component-json
'{"SLIPPAGE_BPS": 10}'` combined with `--portfolio` is silently a no-op:
every one of the 3 slippage cells in the requested grid would produce the
**identical** result, varying nothing.

**Even after fixing that gap, the compute cost is the real blocker.**
`SLIPPAGE_BPS` is itself a real, wired config flag (`edge/frictions.py`,
`swingbot/config.py`) — unlike some of E33's fictional assumed flags, so
fixing the threading gap (the same `tickers=`-style override pattern
already added to `run_folds`/`run_backtest_range.py` for E80) is a small,
legitimate change. But the brief's own 3x3 grid (3 slippage levels x 3
risk levels = 9 cells) each requires a full portfolio-replay pass —
Run 1 above took **~88 minutes** for exactly one such pass. Nine of them
sequentially is **~13 hours** of continuous compute, before even
considering that risk-level variation doesn't need a re-run at all
(`portfolio_replay`'s own `risk_pct` argument can be swept over the
*same* collected signals — only the 3 slippage levels actually require
distinct signal collection, cutting the real cost to ~3 runs / ~4.5
hours, still a genuinely long unattended job).

**Recommendation for whoever picks this up:** thread a `slippage_bps`
override through `collect_portfolio_signals` (mirroring E80's `tickers=`
pattern), then run only the 3 slippage-level signal collections (not 9),
sweeping `risk_pct` locally over each collection's already-gathered
signals via `portfolio_replay(signals, risk_pct=r)` for the 3x3 table —
cutting the real compute from ~13 hours to ~4.5. Not done this session:
it's a real code change plus a multi-hour run, and per the phase's own
established pattern (E77's production flip, E84/E85's live-telemetry
gates), a job of that scale gets flagged for an explicit decision, not
launched silently.
